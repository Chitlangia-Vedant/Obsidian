# Deep Dive
## 1. The partitioned log

The event in a partition can be stored as
- SQL DB
- NoSQL DB
- Write Ahead Log-WAL (Default)

Each partition is an append-only log file. The broker writes messages sequentially, assigns each one a monotonically increasing **offset**, and never modifies entries in place.

This structure supports high throughput because appending to a file and reading forward from an offset are efficient disk operations. 

The broker does not update an index, lock rows, or perform random seeks for each message(Like when using SQL or NoSQL).
## 2. Consumers, offsets, and delivery semantics
Consumers **pull** messages and track an **offset** for their position in each partition. A slow consumer falls behind instead of being overwhelmed, while the messages remain safely on disk.

Within a **consumer group**, assign each partition to one member so only one consumer processes each message. Two separate groups reading the same topic each receive every message, which provides pub/sub behavior with the same mechanism.

Offset commits are where delivery semantics are decided:

- **Commit before processing** gives at-most-once. If the consumer crashes after committing, that message is never processed.
- **Commit after processing** gives at-least-once. If the consumer crashes after processing but before committing, the message is redelivered.

Use at-least-once delivery by default. Wherever the consumer commits its offset, a crash can occur between processing and acknowledgement. Exactly-once _processing_ is still possible when consumers are idempotent and can safely handle a redelivery.
## 3. Replication and broker failure
Each partition has a leader and some number of followers on other brokers, which is leader-based replication applied per partition. Producers write to the leader; followers pull from it and append the same messages in the same order.

Choose **when to acknowledge a write**. 
- Acknowledging after the leader receives it is fast but can lose data if the leader dies before replication. 
- Waiting for a quorum of in-sync replicas adds latency but survives one broker loss. 
Make this choice per topic because metrics and payment events may need different durability guarantees.

When a broker dies, promote a follower. Track which replicas are **in sync** because promoting a lagging follower would lose messages it had not received. Let the strongly consistent metadata store decide the new leader so two brokers never lead the same partition simultaneously.

## 4. Retention and replay
Because consumers track their own offsets, the broker does not need to delete a message after it is read. Retaining messages lets a consumer reset its offset after a bug and reprocess history. A new consumer can also start from the beginning of the retained log.

Delete whole log segments when they age out instead of scanning individual messages. An alternative policy, **compaction**, retains only the newest message for each key and turns the topic into a changelog of current state.

# Common pitfalls
- **Promising global ordering.** It requires a single writer and doesn't scale.
- **Claiming exactly-once delivery.** Explain the gap between processing and acknowledging instead.
- **Pushing to consumers.** Push overwhelms slow consumers; pull lets them fall behind harmlessly.
- **Ignoring in-sync replica tracking.** Promoting a lagging follower silently loses acknowledged messages.
- **Choosing a low-cardinality partition key.** Creates hot partitions that cap throughput regardless of how many brokers you add.
